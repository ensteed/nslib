*** In vulkan, if I enable device extensions in one device, but another device does not need them, should I just use the EXT function for both? Or do I need to have some kind of logic to decide which to use?

You need logic per /VkDevice/.

In Vulkan, an extension’s commands are only valid on a device if you *enabled that extension when creating that VkDevice*. If you call an =VK_EXT_*= function (or any extension command) on a device where the extension wasn’t enabled, behavior is invalid (typically you’ll just crash because the function pointer is =NULL=, or you’ll hit validation errors).

Practical approach:

- *When you create each VkDevice*:
  1. Query supported device extensions for that physical device.
  2. Decide which extensions you will enable for /that device/.
  3. Create the device with that extension list.

- *When you use extension functionality*:
  - Either branch on “is extension enabled for this device?” (store a boolean in your per-device struct), *or*
  - Load function pointers per device and only call them if non-null.

Notes:
- =vkGetDeviceProcAddr(device, ...)= is *device-specific*. Don’t assume a function pointer you got from one device is usable with another.
- If an extension is supported and you don’t mind requiring it everywhere, you /can/ just enable it on all devices you create (where supported). But you still must handle the case where a device doesn’t support it at all.

Rule of thumb: keep a per-device capability/extension table and branch (or fallback) accordingly.

*** Okay, what if a device does support the extension, but its also core. Can I just enable the extension and use the EXT functions to satisfy both? (rather than using the non ext version on the device that also supports it as core)?

Yes, you can do that, as long as you follow two rules:

1) *The extension must be enabled on that VkDevice* (even if the functionality is core on that Vulkan version).  
   In Vulkan, /extension commands are only valid to call if the extension is enabled/, regardless of whether an equivalent core command exists.

2) *You must load the =...EXT= entrypoints for that device* (via =vkGetDeviceProcAddr=) and check they’re non-NULL.

So a common portability strategy is:

- If a device only has the feature via *=VK_EXT_*=*, enable the extension and call =vkCmdSomethingEXT=.
- If a device has it in *core* (e.g., Vulkan 1.2/1.3), you have two options:
  - Prefer calling the *core* command (no extension enabling required).
  - Or *also enable the extension* (if supported) and always call the *EXT* command for uniform code paths.

Caveats / best practice:
- Sometimes the core and extension variants are “the same” but not always perfectly identical in wording/flags/struct chains. Check the spec for that specific feature.
- If you want “one code path,” many engines do:
  - Use core if available,
  - Else fall back to extension,
  because it avoids needing to enable extra extensions on newer devices.

But technically: *using the EXT functions everywhere is fine if you also enable the extension everywhere you plan to call them.*

*** So I still have to load the EXT functions manually? They are not loaded automatically by enabling the extension?

Yes. Enabling an extension does *not* automatically give you callable C function symbols/addresses.

In Vulkan you must obtain function pointers:

- *Instance-level commands*: via =vkGetInstanceProcAddr(instance, "vkFooEXT")=
- *Device-level commands*: via =vkGetDeviceProcAddr(device, "vkCmdFooEXT")=

What enabling the extension does is make those commands *valid to use* for that instance/device. It does not “link” or auto-populate pointers for you.

Notes:
- Many loaders/headers make /core/ functions look like normal linked symbols, but *extension functions are typically =NULL= unless you fetch them* (unless you use a helper loader).
- You can use a library to avoid manual work (e.g. *volk*, *glad*, *Vulkan-Hpp’s dispatcher*), but under the hood they still call =vkGet*ProcAddr=.

So: enable extension + load its function pointers (per instance/device as appropriate) + only call them when enabled.

*** If the function is not core, will the function (ie vkCmdSetCullMode) be null?

- =vkCmdSetCullMode= is a *core* command in Vulkan *1.3* (and also available via =VK_EXT_extended_dynamic_state= as =vkCmdSetCullModeEXT=).

That pointer can be NULL if:
- the extension wasn’t enabled on that =VkDevice=, or
- the extension isn’t supported by that device/driver.

For *core commands* (like =vkCmdSetCullMode= on a Vulkan 1.3 device), you normally call them directly via the loader (or via whatever dispatch system you’re using). If you instead try to fetch them with =vkGetDeviceProcAddr=, you should generally get a valid pointer when the device supports that core version—but you don’t typically rely on “NULL vs non-NULL” to decide core availability. *** what is volk for?

Volk is a small Vulkan “meta-loader” library that takes care of loading Vulkan function pointers for you.

What it solves:

- In Vulkan, many functions (especially extension functions, and sometimes even core ones depending on how you’re set up) must be obtained via:
  - =vkGetInstanceProcAddr=
  - =vkGetDeviceProcAddr=
- Doing that manually for dozens/hundreds of entry points is tedious and error-prone.
- Volk centralizes that: you call a couple init functions and then you can call Vulkan functions normally, including extension functions, without writing all the pointer-loading boilerplate.

Typical usage:

1) Initialize the global loader (loads =vkGetInstanceProcAddr= etc):
#+begin_src c
volkInitialize();
#+end_src

2) After creating a =VkInstance=:
#+begin_src c
volkLoadInstance(instance);
#+end_src

3) After creating a =VkDevice=:
#+begin_src c
volkLoadDevice(device);
#+end_src

After that, extension commands like =vkCmdSetCullModeEXT= are available as normal functions (as long as the extension is enabled). Volk essentially fills in the global function pointers for the “current” instance/device.

Why it’s useful for your crash scenario:

- It won’t magically make unsupported commands work, but it makes it much easier to:
  - Load the right function pointers for the device you created
  - Avoid calling a NULL extension pointer by accident (you can still check support/enabling)

Caveats:

- Volk uses global function pointers, so if you use /multiple VkDevice objects at the same time/, you must reload (=volkLoadDevice=) before issuing calls for a different device, or use volk’s per-device dispatch features/patterns. Most apps only use one device, so it’s fine.
- You still must /check the Vulkan version / enabled extensions/ and only use commands that are actually supported.

Alternatives: glad (Vulkan loader), Vulkan-Hpp’s dynamic dispatcher, or writing your own loader.

*** so volk would make it so vkCmdSetCullMode points to the correct address so my actual could can use the extensionless versions of the function?

Not quite.

Volk doesn’t “upgrade” extension functionality into the core, extensionless name. It just loads whatever entrypoints exist for the instance/device into function pointers.

For your specific case:

- If the runtime/device really supports *Vulkan 1.3*, then the core entrypoint =vkCmdSetCullMode= exists and volk will load it, and calling =vkCmdSetCullMode= is fine.
- If the runtime/device is *< 1.3*, then =vkCmdSetCullMode= is /not a valid command to call/. Volk can’t make it work. You must use the extension command:
  - enable =VK_EXT_extended_dynamic_state=
  - call =vkCmdSetCullModeEXT=

So volk helps mainly by:
- making =vkCmdSetCullModeEXT= callable without you manually doing =vkGetDeviceProcAddr(...)=, and
- ensuring you’re not accidentally using an uninitialized function pointer.

*** Couldn't i have a global function pointer - CmdSetCullMode, and set it to either the ext function or the core function at startup?

Yes, that’s a common and good pattern.

You create your own function pointer type matching the signature, then at startup (per /VkDevice/, really) you set it to either the core or EXT entrypoint, and your code calls your pointer.

Example:

#+begin_src c

    VkCommandBuffer, VkCullModeFlags);

PFN_CmdSetCullMode CmdSetCullMode = NULL;

void init_cmds(VkPhysicalDevice phys, VkDevice dev) {
    VkPhysicalDeviceProperties props;
    vkGetPhysicalDeviceProperties(phys, &props);

            if (VK_API_VERSION_MAJOR(props.apiVersion) > 1 ||
        (VK_API_VERSION_MAJOR(props.apiVersion) == 1 &&
         VK_API_VERSION_MINOR(props.apiVersion) >= 3)) {

        CmdSetCullMode = (PFN_CmdSetCullMode)
            vkGetDeviceProcAddr(dev, "vkCmdSetCullMode");
    } else {
        CmdSetCullMode = (PFN_CmdSetCullMode)
            vkGetDeviceProcAddr(dev, "vkCmdSetCullModeEXT");
    }

    // You should also assert CmdSetCullMode != NULL, and ensure the EXT is enabled if using EXT.
}
#+end_src

Important caveats:

- /If you pick the EXT path/, you must have enabled =VK_EXT_extended_dynamic_state= when creating that /VkDevice/, and the pipeline must include the corresponding dynamic state.
- /Don’t make it truly “global” if you might have multiple VkDevice objects./ Function pointers returned by =vkGetDeviceProcAddr= are effectively tied to that device’s dispatch. Store it in your per-device context, or ensure you never mix devices.
- Prefer checking both: core-1.3 available /or/ extension supported+enabled; don’t rely only on version.

This wrapper-pointer approach is essentially what many engines do for “core vs extension alias” commands.

*** What is the VKAPI_PTRY?

It’s =VKAPI_PTR= (not =VKAPI_PTRY=): a macro from the Vulkan headers that expands to the correct calling convention for function pointers on the current platform/compiler.

Why it exists:
- On Windows, Vulkan functions use a specific calling convention (historically similar to =__stdcall=).  
- On most other platforms it typically expands to nothing.
- If you omit it, your function pointer type can have the wrong ABI on some platforms, leading to crashes when you call through the pointer.

So you should write function pointer types like:

#+begin_src cpp
using PFN_MyCmd = void (VKAPI_PTR*)(VkCommandBuffer, ...);
#+end_src

and not plain =void (*)(...)= if you want to be strictly correct/portable.

(You’ll also see related macros like =VKAPI_ATTR= used on the function /declaration/ side rather than the pointer side.)
