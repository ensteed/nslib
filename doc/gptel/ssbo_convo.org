For infrequently changing SSBO data, you want to avoid synchronization stalls while keeping the implementation simple. Here are the three best strategies:

*** 1. The Simple Path: =glBufferSubData=
If the updates are small or truly rare, this is the easiest to implement.
-   *Pros:* Simple, no manual sync required.
-   *Cons:* Can cause a pipeline stall if the GPU is currently reading that buffer.
-   *Best for:* Small batches of instance data.

*** 2. The Performance Path: Persistent Mapping
Map the buffer once at creation and keep the pointer for the lifetime of the app.
-   *How:* Create the buffer with =GL_MAP_WRITE_BIT | GL_MAP_PERSISTENT_BIT | GL_MAP_COHERENT_BIT=.
-   *Pros:* Zero-copy; no driver overhead from frequent mapping/unmapping.
-   *Cons:* You must manage synchronization yourself (using =glFenceSync=) if you update while the GPU might be rendering.
-   *Best for:* When you want the lowest possible CPU overhead.

*** 3. The "Orphaning" Path: =glBufferData=
Tell the driver you no longer care about the old data by passing =NULL= before uploading the new set.
#+begin_src cpp
glBindBuffer(GL_SHADER_STORAGE_BUFFER, ssbo);
glBufferData(GL_SHADER_STORAGE_BUFFER, size, NULL, GL_DYNAMIC_DRAW); // Orphan
glBufferSubData(GL_SHADER_STORAGE_BUFFER, 0, size, new_data);
#+end_src
-   *Pros:* Prevents stalls because the driver allocates a new memory block behind the scenes.
-   *Cons:* Causes internal memory re-allocation.
-   *Best for:* Replacing the /entire/ instance list at once.

*** Recommendation
-   *If updating a few instances:* Use =glBufferSubData=.
-   *If updating the whole list:* Use *Orphaning*.
-   *If performance is critical:* Use *Persistent Mapping* with a double-buffer (ping-pong) setup to ensure the GPU never reads what you are writing.

Since your SSBO is *shared* across all Frames-in-Flight (FIF) and permanently mapped, you have a *read-after-write hazard*: Frame 1 might write to the SSBO while Frame 0 is still reading from it.

The "Update Slot" idea is good, but for a shared buffer, you need a *Global Versioning* strategy combined with a *Dirty Range* tracker.

*** The Strategy: Global Versioning + Dirty Tracking

1.  *Maintain a CPU-side Master Copy:* Keep the "source of truth" in standard system RAM.
2.  *Track "Dirty" State:* Use a bitset or a list of modified ranges (e.g., =std::vector<Range>=).
3.  *FIF Versioning:* 
    *   Maintain a global =CurrentVersion= counter (incremented whenever data changes).
    *   Each FIF tracks its =LastAppliedVersion=.

*** How the "Update Event" works:
When a FIF begins:
1.  *Check:* Is =FIF.LastAppliedVersion < Global.CurrentVersion=?
2.  *Act:* If yes, the FIF must apply /all/ changes accumulated since its last run.
3.  *Update:* =FIF.LastAppliedVersion = Global.CurrentVersion=.

*** Handling Overlapping Updates (Your Concern)
If Frame 0 updates instance $A$, and Frame 1 updates instance $A$ again before Frame 2 runs:
-   *The Overwrite is a Feature:* Because the FIF only cares about the /latest/ state of the data before it executes, Frame 2 simply copies the most recent data from your CPU Master Copy. The intermediate state from Frame 0 is irrelevant for Frame 2.

*** The Critical Problem: Synchronization
Because the SSBO is *shared*, you cannot simply write to it just because a FIF needs an update. If Frame 0 is still rendering, and Frame 1 (the next FIF) updates the shared SSBO, Frame 0's data will be corrupted mid-draw.

*Two solutions to fix this:*

1.  *SSBO-per-FIF (Recommended):*
    Instead of one shared SSBO, have one SSBO per FIF. Each FIF checks the =Global.CurrentVersion= and updates its /own/ buffer from the CPU Master Copy. This is the most "Vulkan-style" robust approach.

2.  *The Range-Lock / Fence Approach (If you must use one SSBO):*
    You must use =glFenceSync=. Before a FIF updates a range in the shared SSBO, it must check a fence from the /previous/ FIFs to ensure they are done reading that specific range. This is complex and usually results in pipeline stalls.

*Summary Recommendation:*
Use *one SSBO per FIF*. Use the *Global Versioning* logic to decide when a FIF needs to synchronize its local SSBO with the CPU Master Copy. This avoids all race conditions and minimizes redundant data transfers.

*Analyzing Update Mechanisms*

In modern engines, the approach depends on the scale of your material library. Here is the breakdown:

*** 1. Small to Medium Scale: SSBO per FIF (The "Easy" Way)
If your material count is in the low thousands (e.g., 2,000 materials $\times$ 128 bytes $\approx$ 256KB), most engines use an *SSBO per FIF*.
-   *Why:* It is "worry-free." Each frame has its own private sandbox. You simply copy the current CPU state of all materials into the current FIF's SSBO at the start of the frame.
-   *Pros:* Zero synchronization complexity; no fragmentation.
-   *Cons:* Wastes memory if you have 100,000+ materials.

*** 2. Large Scale (AAA): Single Global SSBO + Staging Ring Buffer
Engines like Unreal or Frostbite use a *single, massive SSBO* for all materials to support bindless rendering. They do not duplicate this for every FIF.

*How they update it safely:*
1.  *The Staging Ring:* They maintain a small, persistently mapped *Ring Buffer* (host-visible).
2.  *The Update:* When a material changes, they write the new data into the next available slot in the /Ring Buffer/.
3.  *The Command:* They issue a =glCopyBufferSubData= (GPU-to-GPU copy) from the /Staging Ring/ to the /Global Material SSBO/.
4.  *The Sync:* They use =glFenceSync=. If they need to update Material X, but a fence indicates a previous frame is still using the Global SSBO's old version of Material X, they either stall or (more commonly) write to a new "version" slot in the SSBO.

*** 3. The "Bindless" Hybrid (Modern Standard)
Many engines now use a *Single Global SSBO* but treat it as a *Virtual Heap*.
-   Materials are never updated "in place" while a frame is in flight. 
-   If Material A changes, the engine allocates a /new/ block in the SSBO for the updated data. 
-   The =material_index= passed to the shader for that instance is updated to point to the new location.
-   Old material slots are reclaimed only after a =glFenceSync= confirms no frames are using them.

*** Recommendation
For a custom engine in Emacs/OpenGL:
-   *Use SSBO per FIF* if your total material data is under ~5MB. It is significantly easier to debug and eliminates all race conditions.
-   *Use a Single SSBO + Staging Ring* only if you are hitting memory limits or have a truly massive material library where copying the whole buffer every frame becomes a CPU bottleneck.

*** My engine is actually vulkan

Since you are using *Vulkan*, the "Persistent Mapping" and "Shared SSBO" logic changes slightly because synchronization is now entirely your responsibility.

For *Infrequent Updates* in Vulkan, here are the two industry-standard patterns:

*/ 1. The "Vulkan Way": SSBO per FIF (Parallel Buffers)
This is the most common pattern for instance data.
-   *Setup:* Create $N$ buffers (one per FIF).
-   *The "Update Event" Logic:* 
    -   Maintain a =DirtyRange= list on the CPU.
    -   When a FIF starts, it checks: /"What has changed since I last ran?"/
    -   It copies only those dirty ranges from your CPU Master Copy into its local =VkBuffer=.
-   *Pros:* Zero =vkCmdPipelineBarrier= overhead between frames. No race conditions.
-   *Cons:* $N \times$ memory usage.

*/ 2. The "Modern Way": Single Device-Local SSBO + Staging
For materials, engines usually prefer a single *=DEVICE_LOCAL=* SSBO (faster for GPU to read) and a *=HOST_VISIBLE=* staging buffer.

*The Strategy:*
1.  *The Staging Buffer:* A small, persistently mapped ring buffer.
2.  *The Update:* When data changes, you write the new bytes to the staging buffer.
3.  *The Transfer:* Use =vkCmdCopyBuffer= to move data from Staging to the Global SSBO.
4.  *The Sync:* Use a *=VkBufferMemoryBarrier=*:
    -   =srcAccessMask = VK_ACCESS_TRANSFER_WRITE_BIT=
    -   =dstAccessMask = VK_ACCESS_SHADER_READ_BIT=
    -   This ensures the copy finishes before the shaders start reading.

*/ Dealing with your "Override" Concern
Your worry about Frame 1 overriding Frame 0 is valid. In Vulkan, if you use a *single shared buffer* and update it via =vkCmdCopyBuffer= or direct mapping:
-   *The Risk:* If Frame 0 is still executing on the GPU, and you update the SSBO for Frame 1, Frame 0 might read the /new/ data halfway through its execution (Read-After-Write hazard).
-   *The Fix:* You must treat the SSBO as a *Versioning System*. 
    -   Don't update Material 5 in place. 
    -   Write the "New Material 5" to a new index (e.g., index 100).
    -   Update your Draw Call's =push_constants= or =descriptor_set= for that frame to point to index 100.
    -   Only reclaim index 5 once the =VkFence= for all active frames has cleared.

*/ Summary Recommendation
-   *For Instance Data:* Use *SSBO per FIF*. It’s simpler to manage "dirty" state per frame than to deal with complex GPU versioning/fencing.
-   *For Materials:* Use a *Single Global SSBO* in =DEVICE_LOCAL= memory. Use a staging buffer and =vkCmdCopyBuffer= at the start of the frame. If a material changes frequently, use the "New Index" (Versioning) approach to avoid stalling the pipeline.

*** Would it be faster for the instance data to have it mapped persistantly and just update the mapped memory on updates, or use a staging buffer and have the memory be device local memory?

For per-instance data, *Staging Buffer + Device-Local Memory* is almost always faster for the overall frame time on discrete GPUs.

Since you mentioned updates are *infrequent*, the trade-off is clear:

*** 1. Staging Buffer + Device-Local (Winner)
-   *The Workflow:* CPU writes to Staging (=HOST_VISIBLE=) $\rightarrow$ =vkCmdCopyBuffer= $\rightarrow$ SSBO (=DEVICE_LOCAL=).
-   *Why it's faster:* Shaders read instance data for /every/ vertex/instance, every frame. =DEVICE_LOCAL= memory has significantly higher bandwidth (hundreds of GB/s) compared to the PCIe bus.
-   *The Cost:* A tiny GPU-side copy once in a while. Since your updates are rare, this cost is negligible.
-   *Synchronization:* You need a =VkBufferMemoryBarrier= to transition from =TRANSFER_WRITE= to =SHADER_READ=.

*** 2. Persistent Mapping (Host-Visible/System RAM)
-   *The Workflow:* CPU writes directly to a buffer that the GPU reads over the PCIe bus.
-   *The Problem:* On discrete GPUs, this memory usually lives in System RAM or a small "Base Address Register" (BAR). Every time a shader reads an instance's transform, it has to pull that data across the PCIe bus (usually ~16–32 GB/s).
-   *The Bottleneck:* If you have many instances, you will saturate the PCIe bus, causing the GPU to "starve" while waiting for data.
-   *When to use it:* Only if the data changes *every single frame* and the cost of the copy exceeds the benefit of local reads (rare for SSBOs).

*** The "Best of Both Worlds" Exception: Re-sizeable BAR
If your users have modern GPUs with *Re-sizeable BAR* (AMD Smart Access Memory / NVIDIA Resizable BAR) enabled:
-   You can find a memory heap that is /both/ =DEVICE_LOCAL= and =HOST_VISIBLE=.
-   In this specific case, *Persistent Mapping* is the fastest because you are writing directly into VRAM without an intermediate copy, and the GPU reads it at full local speed.

*** Summary Recommendation
1.  Check for a memory type that is =DEVICE_LOCAL | HOST_VISIBLE=. If it exists and is large enough, use *Persistent Mapping*.
2.  Otherwise (standard behavior), use *Staging + Device-Local*. The GPU's read performance is the priority for per-instance data.
