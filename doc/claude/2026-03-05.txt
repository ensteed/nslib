  ---
  Where to Sort

  Best place: in execute_manifest, per render job, right before the callback is 
  invoked (around line 382).

  // Sort draw calls before handing to callback
  sort_draw_calls(cur_rj->draw_calls);
  if (cur_rj->cb) { ...

  This is the right spot because:
  - All draws have been pushed (full picture is available)
  - Sort happens once per job, close to consumption
  - The callback receives an already-ordered list without needing to know about
  sorting

  An alternative would be adding a sort key to mdraw_call at push_draw time and
  sorting in end_render_frame before execute_manifest. That works too, but
  sorting in execute_manifest keeps the concern local to execution.

  ---
  What to Sort By

  Primary: pipeline (gpu_handle) — pipeline state changes are the most expensive
   GPU state change, so grouping by pipeline is the highest-value sort. This is
  non-negotiable.

  Secondary: mat (rmaterial_handle) — for non-MDI platforms this reduces
  descriptor set rebinds. On MDI platforms the sort still doesn't hurt (draws
  with the same material can batch into a single indirect call).

  Tertiary: geom (rgeom_handle) — reduces vertex/index buffer rebinds. Lower
  value than pipeline/material but free to include in the key.

  What you DON'T need here: texture sorting would be redundant if material
  already encodes texture state (which it typically does through the material
  handle implying texture assignments).

  Translucency caveat: for transparent geometry you'll eventually want a
  separate render job where the sort key is inverted depth (back-to-front)
  rather than pipeline. The existing job-per-pass structure already gives you
  the right place to handle that — just sort differently per job type, or add a
  sort_mode field to mrender_job.

  ---
  Suggested Sort Key

  A packed u64 set at push_draw time on mdraw_call:

  bits [63:48] — pipeline (16 bits)
  bits [47:32] — mat      (16 bits)
  bits [31:16] — geom     (16 bits)
  bits [15: 0] — reserved / depth for transparency

  Adding a u64 sort_key to mdraw_call and computing it in push_draw keeps the
  sort itself trivial (just compare the key integer). It also lets callers
  override the key for special cases like UI z-ordering (you already have
  scissor_override on mdraw_call for UI, so a key override fits the same
  pattern).

  lhs.pipeline < rhs.pipeline || (lhs.pipeline == rhs.pipeline && lhs.mat.index

  ---
  On ditching gen_id from rmaterial_handle:

  The generation exists to catch stale handles — if a material is destroyed and
  a new one takes its slot, an old handle with the previous generation won't
  accidentally resolve to the new material. The question is whether that's a
  real scenario for materials.

  If materials are only ever created at load/setup time and never destroyed
  mid-session (or at least never destroyed while live handles to them could
  still be floating around), the generation buys you nothing and you can safely
  drop it and use a plain u32 index. The is_valid check would just become index 
  != UINT32_MAX or similar.

  If materials can be hot-reloaded or destroyed at runtime while entities still
  hold handles, you want to keep generation — it's what prevents silent
  corruption in that case.

  What's the intended lifetime model for materials in your engine?

❯ Yeah your righ material would never be stale at this point. What if i     
  created a struct of the handles and just hashed the mem to get a sort key 

● Hashing the memory would break the semantic ordering you want. A hash is an
  identity check, not a comparison key — two different pipelines could hash to
  values that interleave their draw calls rather than grouping them. Worse, hash
   collisions between different (pipeline, mat) pairs could group draws that
  need different state, which is a correctness bug (wrong pipeline bound for
  some draws).

  You don't need a single integer key at all. A two-field comparator is simpler
  and correct:

  bool draw_call_less(const mdraw_call &a, const mdraw_call &b)
  {
      if (a.pipeline != b.pipeline) return a.pipeline < b.pipeline;
      return a.mat.index < b.mat.index;
  }

  Then in execute_manifest before the callback, just sort cur_rj->draw_calls
  with that comparator. No key storage needed on mdraw_call, no hashing, and the
   grouping is guaranteed correct.

  The only reason to pack a sort key integer would be if you needed to encode
  priority bits at the front (like opaque-before-transparent, or pass layer
  ordering) — but you already have that naturally since each render job has its
  own draw list and jobs execute in order.

❯ what if i need to support depth sorting? 

● For transparent geometry you need back-to-front depth sorting, which is
  fundamentally incompatible with pipeline/material sorting — you can't have
  both at the same time.

  The standard solution is to separate opaque and transparent into different
  render jobs. Opaque jobs sort by pipeline/mat for performance, transparent
  jobs sort by depth. Since mrender_job already maps to a pass, you'd just push
  a second job for the transparent pass and the sort mode per job naturally
  differs.

  This means mrender_job would need a sort_mode field:

  enum struct mdraw_sort_mode
  {
      PIPELINE,  // opaque: group by pipeline then material
      DEPTH_BACK_TO_FRONT,  // transparent
      DEPTH_FRONT_TO_BACK,  // depth prepass
      NONE
  };

  Then in execute_manifest, pick the comparator based on cur_rj->sort_mode. For
  depth sorting the comparator needs a view-space Z per draw call, which means
  adding a float depth to mdraw_call that the caller populates at push_draw
  time.

  The packed key integer also becomes viable again here if you want — for the
  opaque case you could pack pipeline (upper bits) and mat.index (lower bits)
  into a u128 or use a struct comparator, and for depth just sort on the float.
  Either way the two-comparator approach with sort_mode on the job is the clean
  split.

  index).

  don't want to touch the pipeline creation path right now.

❯ For the transparent geometry - they would have to have whatever state     
  changes necessary to preserve back to front ordering correct? So for      
  those I wouldn't be sorting by pipeline or material at all                

● Right, for transparent geometry the depth order is the only thing that matters
   for correctness — blending breaks if you draw front-to-back. Pipeline and
  material sorting would fight against that.

  The one nuance is that you could do a stable sort — sort by depth first, then
  use a stable sort by pipeline within equal/near-equal depths. But in practice
  floating point depths are almost never exactly equal, so you'd rarely get any
  batching benefit from it. Not worth the complexity.

  So the sort_mode on mrender_job really just needs:

  enum struct mdraw_sort_mode
  {
      NONE,
      PIPELINE,
      DEPTH_BACK_TO_FRONT,
  };

  DEPTH_FRONT_TO_BACK for a depth prepass is another valid one if you ever add
  that, but PIPELINE and DEPTH_BACK_TO_FRONT cover your immediate needs. And
  since transparent jobs need a float depth on mdraw_call, the caller would
  populate that at push_draw time — probably from the view-space Z of the
  object's position.

❯ Is there any benefit to packing the mat/pipeline idx to a 64 bit sort key 
   vs a double member compare on the struct?                                

● No real benefit. With a small number of draw calls per frame the sort is not a
   bottleneck either way. The struct comparator is clearer about intent and
  avoids any packing logic.

  The only case where a packed key wins is if you're sorting millions of
  elements and want to minimize comparator overhead — then a single integer
  compare vs two sequential comparisons matters. At game-renderer scale with
  hundreds to low thousands of draw calls per job, it's noise.

  Stick with the struct comparator.

❯ I was thinking I could have an override in the mdraw_params, and if it is

● The 0 sentinel has a real collision — pipeline index 0 and mat index 0 packed
  together is a valid natural key of 0, so you'd never be able to use the
  default for those. MAX_UINT64 has the same theoretical issue but is
  astronomically unlikely to be a natural packed key.

  The cleanest option is a separate bool override_sort_key flag in mdraw_params
  — no sentinel edge cases at all. But that adds a member just to track the
  state of another member, which is a bit awkward.

  Given your scale a simpler approach: since your pipeline indices and mat
  indices are both small numbers, the upper bits of the packed key will always
  be zero for natural keys. You could reserve the top bit as the override flag:

  // bit 63 set = manual key, lower 63 bits are the key value
  u64 sort_key_override;

  If bit 63 is set, strip it and use the remaining 63 bits as the sort key. If
  0, compute the default. That gives you the sentinel behavior without any
  realistic collision and without an extra bool.

  ```cpp                                                                    
  u64 hash_type(const void*, sizet sz);                                     
  ```                                                                       
                                                                            
  But i don't exactly know how I can compute the hash of that struct using  
  the contents of the atts and not the memory address of the passed in      
  array, in addition to the contents of the other members.                  

● You can't hash the struct directly since atts is a pointer — hashing the
  struct memory would include the pointer value, not the array contents. You
  need to hash the fields separately and combine them:

  u64 hash_framebuffer_cfg(const vkr_framebuffer_cfg &cfg)
  {
      u64 h = hash_type(&cfg.rpass, sizeof(cfg.rpass));
      h ^= hash_type(&cfg.dims, sizeof(cfg.dims));
      h ^= hash_type(&cfg.layers, sizeof(cfg.layers));
      h ^= hash_type(cfg.atts, cfg.att_count * sizeof(VkImageView));
      return h;
  }

  One issue with plain XOR combining though — it's commutative, so hash(A) ^ 
  hash(B) == hash(B) ^ hash(A). For fields of different types/sizes that's
  probably fine, but if two fields happened to hash to the same value they'd
  cancel to zero. A slightly more robust combine is to rotate before XORing:

  h ^= rotl64(hash_type(&cfg.dims, sizeof(cfg.dims)), 27);

  But honestly for a framebuffer key with a small fixed set of heterogeneous
  fields, plain XOR is almost certainly fine in practice.

❯ what would that rotl64 function look like? Would i need to do that for    
  each field? I also want to use this for pipeline config which could be a  
  lot of pipelines is why im asking                                         

● rotl64 looks like this:

  u64 rotl64(u64 x, u32 n)
  {
      return (x << n) | (x >> (64 - n));
  }

  But managing rotation offsets per field gets messy fast, especially for a
  large pipeline config. Better to have a single hash_combine helper and just
  call it for each field:

  void hash_combine(u64 *h, u64 v)
  {
      *h ^= v + 0x9e3779b97f4a7c15ull + (*h << 6) + (*h >> 2);
  }

  Then your framebuffer hash becomes:

  u64 hash_framebuffer_cfg(const vkr_framebuffer_cfg &cfg)
  {
      u64 h = 0;
      hash_combine(&h, hash_type(&cfg.rpass, sizeof(cfg.rpass)));
      hash_combine(&h, hash_type(&cfg.dims, sizeof(cfg.dims)));
      hash_combine(&h, hash_type(&cfg.layers, sizeof(cfg.layers)));
      hash_combine(&h, hash_type(cfg.atts, cfg.att_count *
  sizeof(VkImageView)));
      return h;
  }

  The constant 0x9e3779b97f4a7c15 is the 64-bit golden ratio — it ensures each
  combined value perturbs the hash state in a non-commutative way, so field
  order matters and you don't get cancellation. This is the same approach as
  boost::hash_combine scaled to 64 bits and scales cleanly to as many fields as
  a pipeline config needs.

❯ Could i do all of the struct members in one go, and the atts seperately?  
  For two hash_combine calls                                                

● Only if the struct has no padding between the non-pointer members, and you
  exclude the pointer and att_count from the first hash. The problem is the
  struct as written has mixed types that will likely have padding, and the
  pointer itself is in the middle of it.

  The safer approach is a key struct designed specifically for hashing — reorder
   fields to eliminate padding and exclude the pointer entirely:

  struct vkr_framebuffer_key
  {
      VkRenderPass rpass{VK_NULL_HANDLE};
      uvec2 dims{};
      u32 layers{};
      u32 att_count{};
  };

  Then:

  u64 hash_framebuffer(const vkr_framebuffer_key &key, const VkImageView *atts)
  {
      u64 h = 0;
      hash_combine(&h, hash_type(&key, sizeof(key)));
      hash_combine(&h, hash_type(atts, key.att_count * sizeof(VkImageView)));
      return h;
  }

  No padding, no pointer in the struct, two clean hash_combine calls. The key
  struct also doubles as a clean way to store and compare framebuffer identity
  without dragging the attachment array pointer around.

❯ But a pipeline key would be harder because it has structs within structs, 
   where some nested structs have pointers to data, and i don't want to     
  cater the config struct with a bunch of key type structs                  

● For pipelines specifically you probably don't need to hash the config at all.
  A pipeline is uniquely determined by the technique and the render pass it's
  built for — you already have both of those as small indices. The cache key
  could just be:

  u64 key = ((u64)technique_idx << 32) | (u64)bp_pass_idx;

  That's a perfect hash with no collision risk. The config struct is just the
  input to pipeline creation, not the identity of the pipeline. Two calls with
  the same technique and render pass will always produce the same pipeline, so
  those two values are sufficient as the key.

  The framebuffer case is different because its identity genuinely is its
  configuration — different attachment combinations with the same render pass
  need different framebuffers, so there's no higher-level identifier to use.

❯ What if multiple techniques are using the same shaders/settings for a

● That's a valid concern but it depends on how you define a technique. If two
  techniques are truly identical in shaders and all state for a given pass, they

  technique. The technique handle is effectively the definition of that pipeline

  once at load time and a few duplicates won't affect runtime performance at

❯ So I could run in to platforms where there is padding thrown in? Is there 
   any way to make sure there is no padding on all platforms?               

● Yes, you can use #pragma pack(1) but that can cause unaligned reads which are
  undefined behavior on some platforms (and a real crash on ARM without hardware
   support for it).

  The safer approach is static_assert on the size — it won't prevent padding but
   it will catch it at compile time on any platform where the layout differs
  from what you expect:

  static_assert(sizeof(vkr_framebuffer_key) == 20);

  If it fires on some platform you know you have a padding problem and can fix
  the struct layout. Combined with deliberately ordering fields
  largest-to-smallest (which is what you already did), you'll avoid padding on
  virtually all platforms without needing pragma pack. The assert just catches
  the rare case where a platform surprises you.
