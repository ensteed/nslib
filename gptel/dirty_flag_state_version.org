*** Should I keep a separate dirty flag for update vs rendering? Since my update loop runs at a different frequency.. its a little confusing

**Yes*, you should keep them separate or use a *version counter*.

Because your frequencies differ:

1.  *Update Dirty Flag:* Tracks if logic/physics needs recalculation (e.g., =parent_transform= changed, so =world_transform= needs a re-calc).
2.  *Render Dirty Flag:* Tracks if the GPU data (buffers, uniforms) needs an upload.

*** The Problem with one flag:
If your update runs 3 times before one render, and you clear the flag in the first update, the subsequent updates or the eventual render might miss necessary context.

*** The Better Pattern: Version Counters
Instead of a boolean, use an integer:

-   *Logic:* =state_version++= whenever data changes.
-   *Update Loop:* If =last_processed_version < state

*** Should the state_version be tracked differently for update/render?

**Yes.* You have one *Global Version* and two *Local Trackers*.

Each consumer (Update and Render) must track what version it "last processed" so they don't step on each other's toes.

*** The Layout
1.  *State Version (The Source):* An integer on your object that increments whenever data changes.
2.  *=last_updated_version=:* Stored in your logic/physics system.
3.  *=last_rendered_version=:* Stored in your render system (or component).

*** How it works
-   *Update Loop (e.g., 20Hz):*
    #+begin_src cpp
    if (obj.version > obj.last_updated_version) {
        recalculate_physics(obj);
        obj.last_updated_version = obj.version;
    }
    #+end_src
-   *Render Loop (e.g., 144Hz):*
    #+begin_src cpp
    if (obj.version > obj.last_rendered_version) {
        upload_to_gpu(obj);
        obj.last_rendered_version = obj.version;
    }
    #+end_src

*** Why this is better
-   *Independence:* If the Update loop runs 5 times between frames, the Render loop only reacts once (at the very end) to sync the final state.
-   *No "Clear" Race:* You never "clear" the flag to =false=. You only catch up to the current number.
-   *Thread Safety:* If your loops are on different threads, using an =std::atomic<int>= for the version is much safer than toggling booleans.

*** But what if there are updates that cause update change but not render change?

Split the versions into *two categories*: =logic_version= and =visual_version=.

*/ The Architecture
1.  /logic_version:/ Incremented for /any/ change (timers, AI state, health).
2.  /visual_version:/ Incremented /only/ when properties affecting the GPU change (position, color, texture).

*/ The Flow
In your *Update Loop*, you check if the logic is dirty. If the result of that logic requires a visual change, you bump the visual version.

#+begin_src cpp
void UpdateSystem(Entity& e) {
    // 1. Process Logic
    if (e.data_version > e.last_updated_version) {
        ProcessAI(e);
        e.last_updated_version = e.data_version;

        // 2. Only bump visual version if something visible changed
        if (e.position_changed || e.visibility_toggled) {
            e.visual_version++;
        }
    }
}
#+end_src

*/ Why do this?
- /Efficiency:/ The Render loop only checks =visual_version`. It won't waste time re-uploading buffers just because an AI timer ticked.
- *Granularity:* You can even have multiple versions (e.g., `transform_version` vs `material_version`) if your GPU uploads are expensive.
- *Decoupling:* Your renderer doesn't need to know *what* changed in the logic, only that the "Visual State" is now at a newer number.
